## QA hooks workstream (Part A: audit + registration core + track facade)
**Origin:** dx-qa PLAN.md v1 (2026-07-03, `~/Documents/Work/dx-qa/PLAN.md` §8). dx-qa reads jf-lib's instrumentation as its primary QA signal; the estate's observability holes map exactly to missing library surface. Enforcement/rollout is dx-harness + humans, not dx-qa or this library.
**Idea:** (1) Fable audit of dx-lib, seeded with verified findings: `emitEvent` throws on malformed ticketId/variant *inside its validation* (`src/modules/emitEvent.ts:46-54`), so error-path reporting can swallow the original error — error paths must never throw; pageChange detection is a MutationObserver on `<html>` subtree gated on meta/canonical *presence* + pathname change (`useSPA.ts:540-551`); `watchForRemoval` has a `>= 6` / `>= 5` double boundary (`useSPA.ts:1108,1116`). (2) Design doc + prototype branch for: a registration core factored out of `useSPA` (OBF/static builds get `window.jfLib.experiments[].details` + lifecycle events without SPA machinery); a `track()` facade routing to the platform channel (monetateQ / Test.pageview / ddEvent) while always emitting a structured `jf-wx-track`; auto-tracked resources (tracked `on()`/interval helpers, lib-owned `reset()` teardown, `details.resources` count); `apply:start/done`, `reapply`, `reset:done` phases on a versioned `jf-lifecycle-1.0` event. The design doc must be grounded in consumer usage: survey the most recent builds across 2–3 clients in `~/Documents/Work/jf-conversion/client-files/`, and every proposed hook cites the hand-rolled build pattern it replaces (e.g. per-build `waitForNuxtStable`, hand-rolled `trackMetric`, untracked `addEventListener`). (3) Convert one build — ideally Sam's from-scratch build (w/c 2026-07-06) — as first consumer.
**Context for next agent:** Step (1) is DONE — see `AUDIT.md` (2026-07-03, two rounds: runtime audit + 2.0.11→HEAD delta and consistency sweep); fixes in progress. Surface dx-qa will consume: `jf-pagechange-1.0`, `jf-reinit-1.0`, `window.jfLib.experiments[].details`, `window.jfLib.pagePath`, `#<id>--style` tag convention, and the emitEvent wire events — for those, the `jf-wx-*` names are SANCTIONED FOR RENAME to the versioned family (`jf-err-1.0`/`jf-test-1.0`/`jf-track-1.0`, per AUDIT.md Round 2; "wx" is a retired team name and dx-qa is pre-build so it's a clean break on that side). The real constraints: the existing canary tool listens for `jf-wx-*` (update in lockstep or dual-dispatch for one deprecation window), and 2.0.11 bundles in deployed/historical experiments emit the old names forever — dx-qa listens for both families. jf-conversion's `2.0.11` pin is expected to be lifted, but the estate stays heterogeneous (old inlined bundles), so version-stamp the new surface (capability flags preferred over version sniffing; note 2.0.11 `details` is only `{isRunning, id}` and `experiments[]` holds raw STATE, not `publicApi`). Part B (measuring heuristic→deterministic check delta on a converted vs unconverted build) is blocked on dx-qa `run_flow` v1 existing; that delta is the merge/rollout business case. Ticket-prefixed element classes are per-build discipline today, not a lib convention — the registration core is the fix, not enforcing the class convention.
