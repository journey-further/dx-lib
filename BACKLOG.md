## insertStyle JSDoc falsely promises automatic sweep

**Origin:** jf-conversion `.cursor/rules/jf-lib/` validation sweep against v3.0.1 (2026-07-28) — the rule files had drifted from v2.0.11, and while rewriting them against `dist/declarations/` this claim didn't survive a check against the implementation.
**Idea:** `src/modules/insertStyle.ts:11` tells the caller to use the `<ownerId>--<childId>` id convention "so useSPA resets/destroys sweep this resource automatically." It doesn't. `insertStyle` never registers in `window.jfLib`, and `destroyByPrefix` has no style handling — its own JSDoc (`src/modules/destroyByPrefix.ts:7-11`) correctly lists only the element\* callback registries, `customEvents` listeners, `listeners`, `timers` and `observers`. useSPA removes exactly one style element, the `#<testId>--style` it creates itself in `insertStyleSheet()`. So a style injected via `insertStyle` survives reset unless the caller removes it in their own `reset` callback. Either fix the sentence to say the prefix is a naming convention only and cleanup is the caller's, or make it true — register inserted styles in `window.jfLib.styles[VERSION]` and add a sweep branch to `destroyByPrefix`.
**Context for next agent:** Scoped to `insertStyle` alone. The same sweep sentence appears in `elementReady`, `elementRemoved`, `elementUpdated`, `useEventListener`, `useMutationObserver` and `useSetTimeout`, where it is accurate — those all register and are genuinely swept. Don't "fix" those. Deciding between the two options is the actual work: making it true is the more consistent library (every id-taking module then honours one contract, and it removes a class of leak that no reviewer will reliably catch), but it overlaps the auto-tracked-resources / lib-owned `reset()` teardown design in the QA hooks entry above — if that lands, styles should be swept by that mechanism rather than a bespoke branch. If it's deferred, correct the sentence now, because it currently instructs consumers to skip cleanup they still need. jf-conversion's rule file (`.cursor/rules/jf-lib/insertStyle.mdc`) already documents the caveat accurately and will need updating if the behaviour changes.

## Dispose/undo contract for live re-injection (jf-lib side)

**Origin:** dx-webpack-hmr HMR landscape review (2026-07-17, `dx-webpack-hmr/audit/HMR-LANDSCAPE.md` §5.1) — the highest-value fluidity increment for the live-preview loop, but the API lives in jf-lib, not the plugin.
**Idea:** Variant code (or jf-lib DOM helpers automatically) registers cleanup — `jfLib.onDispose(fn)`, or helpers that record undo ops as they mutate. The dev plugin can then run cleanup and inject the rebuilt bundle in place instead of reloading the page: fluid iteration, and each avoided reload is one less Cloudflare-visible page load. AI-first development makes the convention enforceable — agents can be required to register cleanup in every variant via rulesets/codegen templates, removing the human-discipline blocker that killed this idea historically.
**Context for next agent:** The plugin side is ready to consume it: injection goes through `addCompiledBundle`/`addCodeToPuppeteerDOM` (script-tag replace), so the change is roughly "if `window.jfLib?.dispose` exists, await it and inject in place; else fall back to the state-restoring reload that already shipped". This overlaps heavily with the registration-core/auto-tracked-resources design in the QA hooks entry above — lib-owned `reset()` teardown is the same mechanism; design them as one thing, not two.
